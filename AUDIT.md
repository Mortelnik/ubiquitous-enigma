## Удалённые файлы

- `requirements.txt`, `requirements-min.txt`, `requirements-ml.txt`,
  `requirements-test.txt`: заменены наборами зависимостей в `pyproject.toml`.
- `.env.windows.example`: дублировал `.env.example`; общий шаблон работает в Windows.

Также удалены неиспользуемые импорты и настройки сборки Python-пакета:
проект запускается из исходников через uv и не публикуется как библиотека.
Из обычного Docker-образа исключены тесты, shell-помощники, учебные материалы,
инструменты компиляции и Git. Для необязательной диаризации инструменты сборки
устанавливаются отдельно.

Учебный ноутбук, отчёт, тесты, скрипты обучения/TTS и помощники запуска сохранены:
они относятся к заявленным сценариям. Существующая `.venv`, токены, модели,
загрузки, заметки Obsidian и Docker volumes не удалялись.

## Проверки и ограничения

Дополнение: при проверке истории обнаружено упоминание `scripts/download_balalaika.py`
в старом README, хотя самого файла в доступной истории Git нет. Загрузчик добавлен:
скачивает только используемые текстовые аннотации, фиксирует версию источника и имеет
режим просмотра списка без скачивания. Полная загрузка и обучение ещё не выполнялись.
Режим `--dry-run` проверен на реальном источнике: все пять ожидаемых файлов доступны.
Выбран вариант 1: TF-IDF + LogisticRegression, сравнение реального train с
реальным+TTS. Документы и ноутбук приведены к этому процессу; новые метрики не заявляются.
Добавлен RUNBOOK для Windows. Сравнение фиксирует отпечатки всех выборок, использует
один постоянный baseline и выбирает кандидата по validation macro-F1, а не по test.
Синтез вне train и пересечения ASR с отложенными выборками отклоняются.

Добавлен локальный Windows SAPI-адаптер на Python; политика PowerShell не меняется.
В сессии агента виден русский голос Microsoft Irina, но реальный синтез завершился
ошибкой SAPI (для стандартного английского голоса также получен отказ доступа).
Поэтому успешный синтез на целевом ПК не подтверждён. Перед большим запуском
нужна команда `--check` из RUNBOOK; альтернативный локальный TTS подключается JSON-командой.

- Чистое окружение Python 3.12 установлено командой `uv sync --locked`.
- `uv run --locked pytest -q`: **79 тестов пройдено**. Проверка кэша распознавания
  выполняется с недоступным PyTorch; реальная ASR-модель в тестах не загружается.
  TTS-тесты используют WAV-генератор и не считаются проверкой качества голоса.
- `uv lock --check`: конфигурация согласована с lock-файлом.
- План установки обычного worker для Linux: 77 пакетов, без PyTorch/NeMo/WhisperX.
- План установки дополнительных аудиобэкендов для Linux разрешается без изменения lock-файла.
- Конфигурации Compose CPU и GPU проходят `config --quiet`.
- Ссылки на прежние способы установки удалены из инструкций и скриптов.
- Полная сборка Docker и обработка реальной записи в этой сессии не подтверждены:
  доступ к Docker Engine из среды агента запрещён.
- NeMo/WhisperX и GPU требуют отдельной проверки на целевой машине; разрешение
  зависимостей не подтверждает совместимость драйверов и моделей.
- Обученной модели и исходных данных в репозитории нет. Автоклассификация требует
  обучения `models/style_classifier.joblib`; метрики качества не заявляются.

Это аудит конфигурации и кода проекта, а не полный анализ уязвимостей всех
транзитивных зависимостей. Технические тесты не измеряют качество ASR/TTS и модели.

## Дополнение: CTranslate2 и начальное подключение Telegram

По реальному логу выявлена несовместимость Linux wheel CTranslate2 4.4 с glibc 2.41:
ошибочный флаг PT_GNU_STACK требует исполняемый стек. Новая сборка использует
Debian trixie явно, исправляет флаг через patchelf и проверяет импорт аудиобиблиотек.
Версии математических библиотек и формат модели не меняются; переобучение из-за
этого исправления не требуется. Добавлена отдельная сборка CPU-аудиообраза в CI.
Полная Docker-сборка в сессии агента остаётся непроверенной из-за ограничения доступа
к Docker Engine; новый CI выполняет её на Linux.

Начальный запрос Telegram getMe теперь повторяется с растущей паузой при сетевом
сбое и корректно отменяется при остановке. Повтор отправки сообщений не добавлялся.
Добавлен необязательный TELEGRAM_PROXY_URL для HTTP/SOCKS-прокси VPN-клиента.
Подключение через конкретный VPN/прокси не проверено: адрес и порт пользователем
не предоставлены. Параметр не применяется к внутреннему API и не печатается в логе.


## Дополнение: декодирование Faster-Whisper / PyAV

По журналу worker Faster-Whisper 1.2.1 передавал `metadata_errors` в PyAV 19.0.1,
который не принимает этот аргумент. В uv добавлено ограничение PyAV 16.0.1;
lock-файл обновлён. Проверка аудиосреды при сборке теперь декодирует короткий
WAV через настоящий Faster-Whisper/PyAV без скачивания модели. Ошибка прерывает
сборку. Это также ограничивает PyAV для локального TTS → ASR.

Для Windows также ограничен setuptools<81: CTranslate2 4.4 загружает DLL через
удалённый в новых setuptools модуль pkg_resources. Linux это ограничение не затрагивает.

## Дополнение: результаты, хранилище Windows и Whisper CUDA

Выбор устройства Faster-Whisper теперь использует CTranslate2 независимо от
наличия PyTorch. GPU override устанавливает совместимые с CTranslate2 4.4 библиотеки
CUDA 12/cuDNN 8 через uv, задаёт пути загрузки и включает CUDA/float16. Добавлена
диагностика `python -m app.gpu_check` без скачивания модели. CPU fallback переводит
float16 в int8; отсутствие GPU отражается в результате. Полный инференс на GPU
и новая Docker-сборка в этой сессии не выполнялись.

Опциональный storage override подключает Windows-папку Obsidian к API и worker.
Структурированная классификация показывается в отдельном блоке веб-интерфейса.
Telegram при BOT_SEND_RESULTS=true возвращает стиль, оценку, метрики, фрагменты
текста и относительные пути заметок. При false сохраняется ответ без содержимого.
Диаризация, выключенная оператором, больше не представляется как измерение одного
спикера в веб-интерфейсе и ответе бота. Проверено 86 тестов, синтаксис JavaScript,
uv.lock и совместная конфигурация Compose GPU/storage/bot.

После устранения конфликта с Windows Ollama удалена публикация контейнерного
порта 11434: API/worker используют внутреннюю сеть. Контейнеры успешно запущены,
Redis и Ollama healthy. Диагностика в реальном GPU-worker обнаружила одно CUDA-
устройство, загрузила libcublas.so.12 и libcudnn.so.8 и подтвердила float16.
Само распознавание пользовательской записи на GPU в этой проверке не выполнялось.
